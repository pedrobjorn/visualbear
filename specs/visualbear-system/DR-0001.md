# DR-0001: The merged visualbear system view keeps the /workflow/ URL

- Date: 2026-11-12
- Status: accepted
- Context: The visuAI page (`/workflow/`) and the styleguide (`/styleguide/`) merge into one view named "the visualbear system", switchable by tabs in the hero. The build's routes are directory names (`src/<name>/index.nunjucks`), so "one view" must pick a route. Options:
  1. Keep `/workflow/` as the canonical route.
  2. New route `/system/` (or `/visualbear-system/`) with both old routes retired.
  3. Two routes sharing one shell, cross-linked (rejected as "not combined").
- Decision: Option 1 - the page stays at `/workflow/`; the visualbear system is expressed by the eyebrow/tab chrome, not the URL. Tab switching is client-side (one URL, no per-tab routes).
- Rationale: Both source pages already render at depth 1, so every relative asset path in the styleguide blocks (`../images/...`) resolves unchanged the moment they render inside `/workflow/` - the merge becomes a content move, not a path audit. The existing `/workflow/` references (release-4.0 mirror hrefs from `scripts/release-mirror.js`, DR-0007's marker scope, the docs in `specs/release-4.0/`) all keep pointing at a live page. A new route buys a slightly more literal URL and costs a reference migration plus two dead routes; the wording is carried perfectly well by the hero eyebrow and tab labels.
- Consequences: The view's URL does not say "visualbear system"; anyone grepping for the view name by route finds `/workflow/`. If the view ever splits back out, the tab pair dissolves into the two original routes - the merge is cheap to reverse precisely because no URLs moved.
