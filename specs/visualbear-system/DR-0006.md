# DR-0006: The strip lives inside the active hero; the robot's hover plate takes the chip shape (2026-11-12, Pedro's review round 2)

## Decision

1. **Ticket 14 — the tab strip is hosted by the active panel's hero** ("Make the styleguide hero contain the tab, don't put it below a large hero container").

   Measured on the built mirror at 1440 (design tab active): the strip renders at y=80-125, but `#styleguide_container` starts at **y=900** - the workflow article's `.gallery-container` scaffolding reserves ~775px of empty height above the design panel even with the visuAI panel `[hidden]`. The strip floats stranded at the top; the design system's hero is a full viewport down. The tab neither belongs to the hero above it nor touches the content below.

   **Model: one strip, one live host.** The strip is a single DOM node (single `role=tablist`, valid id contract, one focus point). Each panel carries an empty host slot (`[data-vb-strip-host="<tabid>"]`) as its first child - inside the visuAI panel (dust state: same DOM position the strip renders at today, so the dark state's pixels are unchanged) and inside `#styleguide_container`'s top (the styleguide page's own light `.section`, above its hero article). On activation the tab controller moves the strip wrapper into the active host before the panel paint completes (synchronous, one paint frame - no flash), and back on the reverse switch. The inactive panel is `display: none` and, in the light state, the workflow article collapses entirely (`body.vb-system-light #workflow_container { display: none }`) - no reserved void, the styleguide section starts right under the nav and its hero container wraps the strip.

   Rhythm parity is then structural, not per-state patched: strip top = nav-bottom + 32 (T5's margin, now inside the section), strip -> hero = the same 24 margin the dark state ships, hero's own 64px head padding matches the visuAI hero exactly. The only override needed: the styleguide page's leading `article.text-container` keeps its 32px top padding for its own page, so when the strip hosts, the adjacent-article rule zeroes it (`#styleguide_container > [data-vb-strip-host] + article.text-container { padding-top: 0 }`) - plain adjacent CSS, no `:has()`, no state classes; the host is in the markup permanently.

   Keyboard contract: activation follows focus (WAI-ARIA). Moving a focused node detaches and blurs it, so the controller paints (relocates) FIRST, then sets `focus()` on the already-active tab. Keyboard users keep an unbroken announcement chain (the tablist keeps its aria-label; no second instance ever exists).

   Rejected: **duplicated strip instances per panel** - two `role=tablist`s and duplicated button ids break the naming contract and the `npm test` suite, for no visual gain. **CSS-only breakouts** (negative margins / `:has()`-driven jumps) - keeps the void in the DOM and papers over the structure the ticket is about.

2. **Ticket 15 — the robot's hover red takes the pill's shape** ("make the hover over red match the pill shape"). The global `a:hover` paints `#d73735` on the anchor's 44x44 box with radius 0: a sharp red square sits under the robot while a 999px-rounded chip sits beside it. **Fix:** `a.robot { border-radius: 999px }` - the hover/focus plate renders as a rounded chip in the pill's radius language, same 44x44 hit box, no other token moves. Considered and rejected: wrapping glyph + label into ONE red expanded pill - it would repaint the label chip (its `$vb-light` plate disappears on red) and change the hover's design, which Pedro did not ask for; the label chip keeps its own shape.

## Verification notes

- Both tickets are probed on RENDERED GEOMETRY (the DR-0005 gate rule): strip top/bottom vs nav and hero, red plate radius = 999px while hovered, section top ~= nav bottom (the void gone), and the strip's parentage inside the active panel's hero container.
