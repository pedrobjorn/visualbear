# DR-0008: AI marker — final form: end-of-content label, section-level marking

- Date: 2026-10-29
- Status: accepted
- Supersedes: DR-0007's styling portion (placement/visibility); its scope and production rules stand
- Context: Three visual iterations landed on what Pedro approved: (1) corner chip — invisible on the dark page (dark-on-dark, and the dark-mode override targeted `.cs-black`/`.cs-dark` while this page is `.cs-workflow`); (2) label above the block — visible but wrongly placed; (3) final: label **at the end of the marked content**, with margin around it. A second discovery: the dev server executes the build code it loaded at startup, so renderer changes are invisible until the server restarts — several "it's not working" rounds were stale-server artifacts. A third: section order in `workflow.md` (Quality gates before Design principles) and some closing paragraphs were lost during migration and restored.
- Decision: The `[ai]` marker line in md becomes a standalone `.ai-mark` element (`✦ AI-drafted`, block-level, `width: fit-content`, margin `1.5em 0`) rendered exactly where the marker sits in the source — at the end of the content it attributes. Marking is per-section: one `[ai]` at the end of each content section; **hero and quotes are excluded** (the hero carries its own `data-ai` attribute in the shell; quotes stay unmarked). Production builds strip `.ai-mark` elements + `data-ai` attributes and warn loudly (deep rule unchanged). The `[data-ai]::after` CSS path remains for shell-marked elements. Content rule added: **no em dashes** in any content file (hyphens/colons/restructure) — enforced in `visuaibear-core/copy-principles.md` and the spec templates.
- Consequences: Marker placement is author-controlled via marker position. Dev servers must be restarted after build-code changes (the operator, not the watcher, reloads code). Content fidelity is verified against pre-migration builds with whitespace/normalisation-insensitive diffs.
