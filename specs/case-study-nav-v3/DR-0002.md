# DR-0002: The active (scrolled-to) nav option gets a red accent line, driven by a scroll-spy that actually ships

- Date: 2026-11-24
- Status: accepted ("unredlined" read as "a red line" - ASSUMPTION, plan Open questions; line-color-on-red-bar choice also an open question)
- Brings into scope: specs/case-study-nav/tickets.md Ticket 4 (aria-current scroll-spy), which is Status: TODO - measured 2026-11-24: 0 `aria-current` attributes at runtime, 0 occurrences in `build/scripts/main.js`
- Context: Pedro 2026-11-24: "Add an active state (unredlined) for selected / scrolled to sections". Read as "an active state (a red line) for selected / scrolled-to sections". Today the only active styling is the dead CSS rule `a[aria-current='true'] { text-decoration: underline }` (`_case-study.scss:223`, v2); hover/focus also use the white underline, so underline alone cannot distinguish "you are here" from hover. The bar's own bottom border is `1px solid var(--cs-accent)`, and the site brand red is `$vb-primary: #d73735` (`_variables.scss:37`).
- Decision:
  1. Scroll-spy JS (implements parent Ticket 4): a small scoped script loaded only on pages that render `.cs-index` (the 5 case-study shells; body-class or per-template gate). Vanilla `IntersectionObserver` over the `.cs-section` elements with `rootMargin: -48px 0px calc(-1 * var(--cs-index-h)) 0px` (48px header + 35px bar), so "current" = the section under the stuck bar. Exactly one `.cs-index a[aria-current="true"]` while a section is under the bar; none while the hero/meta zone is under the bar (above the first section). No library, no animation (reduced-motion safe by construction), disconnects when no `.cs-index` exists.
  2. Active visual: `a[aria-current='true']` gets a 3px solid line on the bar's bottom edge inside the button: `box-shadow: inset 0 -3px 0 var(--cs-index-active)` (new token on `.case-study`, default `#{$vb-primary}` = #d73735, the brand red), replacing the underline for the active state; hover/focus keep the white underline. The line sits flush with the bar's own 1px `--cs-accent` border, so the active segment reads as a thickened colored segment of the bar. Token per theme where the head background is already red (digital-closet `--cs-head-bg` #d73735): override `--cs-index-active: #fff` so the line stays visible (open question for Pedro).
  3. `title` attribute on each nav anchor carries the full (uncondensed) label, so ellipsized buttons stay accessible by name.
- Rationale: a line indicator is state, not decoration: it survives hover (which only underlines), is visible without color dependence when paired with the white `:focus-visible` outline elsewhere, and uses the brand red Pedro named ("red line") instead of inventing a fill. The spy is the behavior the parent spec already specified but never shipped; measuring showed the CSS half existed with no JS half, so this DR lands both together.
- Consequences: new `src/_scripts/cs-index.js` (or a gated block in the main bundle) + template/script-loader wiring; `.case-study` gains `--cs-index-active`; `_case-study.scss` `a[aria-current='true']` changes from underline to the inset line; `cs-nav.test.js` gains source assertions (token exists, aria-current rule uses the token, no underline on aria-current); Playwright acceptance: scroll to `#discovery` on teachr at 1440 -> exactly one aria-current, on `a[href="#discovery"]`, computed `box-shadow` contains the line color; scroll to top -> zero aria-current.
