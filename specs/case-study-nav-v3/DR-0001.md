# DR-0001: The nav bar matches the body content width; the option buttons expand to fill it equally

- Date: 2026-11-24
- Status: accepted (equal-fill reading is an ASSUMPTION - see plan Open questions)
- Supersedes: specs/case-study-nav-v2/DR-0002 at the BAR level (v2 pinned the bar's left edge to the body element edge x=0); refines v2 DR-0005 (group-centered row) - the row now fills the bar, so centering becomes moot
- Context: Pedro 2026-11-24: "Expand the nav options to match the width of the rest of the body content." Measured 2026-11-24 (evidence/measurements-2026-11-24.md): the body content column is `.document-text` = `$content-width: 916px` border-box (`_variables.scss:40`, one content width site-wide per ticket 42 / DR-0013), i.e. section text and the meta band span left 278 / right 1162 (884px) at 1440x900, 16/752 at 768, 16/374 at 390. The nav today is full-bleed 0..1440 at every width (`width: 100vw; margin-left: calc(50% - 50vw)`), so at desktop it is 556px wider than the content it indexes; the link row is centered in that oversized bar (teachr row 781px). Readings considered: (a) bar shrinks to the content column, buttons keep natural width and stay centered; (b) bar shrinks to the content column AND the buttons expand (flex grow) so the five options share the full content width equally, like a tab strip.
- Decision: (b). `.cs-index` drops the full-bleed pair and becomes a normal block in `.document-text` (`width: 100%` of the content box), so its edges equal the body content edges: left/right 278/1162 at 1440, 16/752 at 768, 16/374 at 390. `.cs-index ul` keeps `display: flex; gap: 0` but `justify-content` becomes irrelevant; `li { flex: 1 1 0; min-width: 0 }` and `a.btn { width: 100% }` make the max-5 buttons equal-width and flush, together spanning exactly the bar width (1440: 884/5 = 176.8px per button). Buttons still touch (gap 0) and each anchor is still full bar height (35px). Long labels that exceed the button width get `overflow: hidden; text-overflow: ellipsis; white-space: nowrap` on the anchor plus a `title` attribute carrying the full label (edge behavior, replaces the 768/390 internal scroll strip as the primary overflow strategy - ASSUMPTION, see Open questions).
- Rationale: "match the width of the rest of the body content" names the content column, not the viewport; "expand the nav options" says the options themselves grow to fill it, which is the (b) tab-strip reading and also fixes the measured overflow of sports' 1052px row past the 884px column at desktop. Equal widths make the bar read as one segmented control aligned with the text edges above and below it. Keeping the bar content-width while stuck (top 48, z-index 1, opaque `var(--cs-head-bg)`) means the stuck bar floats centered over the page under the header, same width as the content scrolling beneath it; making it full-bleed only when stuck would need position:fixed and a second height pin, rejected as complexity for no requested behavior.
- Consequences: `_case-study.scss` `.cs-index` loses `width: 100vw` / `margin-left: calc(50% - 50vw)`; `ul` loses `justify-content: center` (or keeps it harmlessly when the row overflows); `li`/`a` gain the flex-grow rules; `--cs-index-h` stays 35px (height unchanged); `cs-nav.test.js` source assertions change from "full-bleed" to "no 100vw / no 50vw margin" + `flex: 1 1 0` on li; Playwright acceptance changes to: `.cs-index` rect left/right == first `.cs-section` content rect left/right at 1440/768/390; row width == bar content width; all buttons equal width within 0.5px; bar still sticks at top 48 with header-matched bg.
