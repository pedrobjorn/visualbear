# DR-0005: the bar stays full-bleed (the pre-v3 menu was correct); the LINK ROW is constrained to the body content width and the options spread to fill it

- Date: 2026-11-24
- Status: accepted
- Supersedes: DR-0001 at the BAR level only. DR-0001's row-level decisions stand unchanged (equal-fill `li`/`a.btn`, ellipsis + `title` edge).
- Context: Pedro 2026-11-24, correcting the same-day request "Expand the nav options to match the width of the rest of the body content": "The menu was correct before, it should be full width. The LINK OPTIONS are what should be limited to the width of the content container, and spread to take up the space." DR-0001 (shipped as 4139434) read "the nav" as the bar and shrank `.cs-index` itself to the content column, so the stuck bar floated centered under the header instead of reading as its extension (captures in evidence/t2-verify.md). The pre-v3 bar was full-bleed 0..viewport at every width (`width: 100vw; margin-left: calc(50% - 50vw)`) and Pedro confirms that was correct. Measured content column (evidence/measurements-2026-11-24.md): `.document-text` = `$content-width: 916px` border-box (`_variables.scss:40`) with `padding: 0 16px` (edge-alignment DR-0002), so section content edges are 278/1162 at 1440, 16/752 at 768, 16/374 at 390.
- Decision: `.cs-index` keeps the full-bleed pair - the BAR spans the viewport at every width and, stuck at top 48 with opaque `var(--cs-head-bg)`, matches the fixed header edge-to-edge. The content-width constraint moves to the link row: `.cs-index ul` gets `width: calc(100% - 32px); max-width: calc(#{$content-width} - 32px); margin: 0 auto;` (32px = 2 x the 16px `.text-box` padding), so the row's edges equal the `.cs-section` content edges at every viewport. The max-5 options keep spreading to fill the row (DR-0001 row level): `li { flex: 1 1 0; min-width: 0 }`, `a.btn { width: 100%; justify-content: center; overflow: hidden; text-overflow: ellipsis; white-space: nowrap }` - 884/5 = 176.8px per button at 1440. `ul` keeps `gap: 0` (buttons touch), `overflow-x: auto` as fallback, `justify-content: center` as a harmless no-op. Bar mechanics unchanged: sticky top 48, z-index 1, padding 0, height auto, `--cs-index-h: 35px`; gap cover->nav stays 0 (the full-bleed pair is horizontal only - re-verified with /tmp/measure_gap.py after the change).
- Rationale: the bar is chrome - the fixed header and the hero cover are full-bleed too, and a stuck full-bleed bar reads as the header's extension. The links are content and should align with the text column they index. Constraining the row to the content width and spreading the options equal-fill gives the tab-strip alignment with the section edges, while the bar keeps its pre-v3 full width. This is the literal reading of Pedro's correction.
- Consequences: `_case-study.scss` `.cs-index` regains `width: 100vw` + `margin-left: calc(50% - 50vw)`; `ul` gains the `width: calc(100% - 32px)` / `max-width: calc(#{$content-width} - 32px)` / `margin: 0 auto` trio; `li`/`a.btn` rules unchanged from 4139434; renderer unchanged (`title` already shipped). `cs-nav.test.js`: the no-`100vw` assertions flip back to requiring the full-bleed pair on `.cs-index`, plus new source assertions on the `ul` width/max-width/margin; the li/a and `title=` assertions from Ticket 2 stay. Playwright AC: bar rect 0..viewport at 1440/768/390; `ul` rect == first `.cs-section h2` rect within 0.5px; row fills the ul; 5 anchors equal within 0.5px and touching; anchor height == bar - 1; gap cover->nav == 0; stuck bar full-bleed at top 48 with header-matched bg; at 390 no page-level h-scroll, ellipsis computed, `title` present.
